# Glossary

## Constitution

Главный документ проекта. Он задает неоспоримые правила для архитектуры, workflow, языковой политики и governance. Для новых проектов также служит техническим фундаментом, фиксируя технологический стек и базовую архитектуру.

## Spec

Документ уровня фичи, который описывает, что должно быть построено и зачем.

## Inspect

Фаза проверки, которая смотрит spec и связанные артефакты на полноту, согласованность и соответствие конституции.

## Plan

Опциональная (opt-in) техническая фаза проектирования, которая переводит одну spec в артефакты, пригодные для реализации. Используется только когда фиче нужен дизайн; маленькие/низкорисковые фичи идут сразу к tasks.

## Propose

Полоса по умолчанию для новой фичи: `spec.md` + `tasks.md` за один проход, плюс `data-model.md` или `contracts/*`, если изменение реально их затрагивает. `plan.md` не пишет; неуверенность остаётся в `## Open Questions`, и только жёсткие сигналы (несколько фич, ломающее изменение или миграция схемы, работа на другом сервисе) эскалируют в `/spk-spec`.

## Feature Artifact Set

Набор файлов под `specs/active/<slug>/`, обычно включающий `spec.md`, `plan.md`, `tasks.md`, `data-model.md`, `verify.md`, `contracts/` и optional `research.md`.

## Tasks

Исполнимая декомпозиция spec (и плана, если он есть). В SpecKeep `tasks.md` лежит внутри feature artifact set, рядом с `plan.md`, когда этот артефакт существует.

## Implement

Фаза исполнения, которая стартует от незавершенных задач и обновляет состояние tasks.

## Verify

Легкая post-implementation проверка, которая подтверждает, что фича достаточно согласована с tasks, spec, plan artifacts и правилами проекта, чтобы безопасно двигаться к archive или заявлению о завершенности.

## Archive

Фаза и область хранения, которые используются для сохранения исторического снимка завершенного или неактивного feature package.

## Finish

Локальное закрытие: archive + коммит снимка + `merge --no-ff` в базовую ветку + удаление локальной feature-ветки. Никогда не пушит и не удаляет remote-ветки.

## Archive Status

Причина, записанная в архивном пакете: `completed`, `superseded`, `abandoned`, `rejected` или `deferred`. Только `completed` требует закрытых задач, `Proof:` и соблюдения verify-policy; остальные статусы паркуют незавершённую работу и требуют `--reason`.

## Proof

Строка evidence под завершённой задачей в `tasks.md`: `Proof: <kind> <path> [<anchor>]`. `trace`, `check`, `doctor` и archive-гейт читают только эти строки.

## Converge

Дешёвый цикл закрытия: перепроверяет завершённые задачи, `Proof:`, заявленные поверхности и покрытие AC, сообщает пробелы, чтобы добавить follow-up задачи и повторить проверку. Легче `verify` — файл отчёта не создаётся.

## Grill

Опциональное pre-spec интервью: раскрывает design tree раундами с рекомендацией по каждому вопросу. По умолчанию артефактов не пишет.

## Diagnose

Опциональный ограниченный цикл диагностики бага: reproduce → minimize → hypothesize → instrument → fix → regression test. Если причина известна — используйте hotfix.

## Resume

Тонкая передача состояния внутри сессии: короткий пакет (фаза, задачи, следующая открытая задача, блокеры), артефакт не создаётся. Если состояние нужно передать человеку — используйте handoff.

## Handoff

Разделяемая сводка текущего состояния фичи, чтобы другая сессия или коллега продолжили без перечитывания набора артефактов.

## Hotfix

Аварийная полоса вне цепочки фаз: известная причина и небольшой ограниченный diff.

## Data Model

Plan-артефакт, который описывает сущности, структуры, связи и важные invariants, нужные для реализации.

## Contracts

Plan-артефакты, определяющие интерфейсы, например API, события или другие внешние границы взаимодействия.

## Research

Опциональный plan-артефакт, который нужен только тогда, когда нужно сохранить неопределенность, внешнее исследование или архитектурный tradeoff.

## Agent Target

Поддерживаемая агентная экосистема, для которой SpecKeep может генерировать project-local command или prompt files, например `claude`, `codex`, `copilot`, `cursor`, `kilocode`, `opencode` или `trae`.

## Orphaned Agent Artifact

Сгенерированный agent file, который все еще лежит на диске, хотя его target уже не включен в `.speckeep/speckeep.yaml`.

## Docs Language

Настроенный язык, который используется для генерируемой проектной документации, такой как `constitution.md`, specs, plans и tasks.

## Agent Language

Настроенный язык, который используется для generated prompts и guidance в `AGENTS.md`.

## Comments Language

Настроенный предпочитаемый язык для новых или измененных комментариев в коде во время реализации.

## Given / When / Then

Канонические BDD-маркеры, которые используются в acceptance criteria независимо от языка документации. Текст вокруг них при этом может следовать настроенному docs language.

## Acceptance ID

Стабильный идентификатор критерия приемки, например `AC-001`. Он помогает делать traceability явным между spec, tasks и inspect-отчетами.

## Traceability (Прослеживаемость)

Практика связывания доказательств реализации (файлов и тестов) с задачами и критериями приемки с помощью стабильных ID. В SpecKeep доказательства фиксируются как записи `Proof:` в `tasks.md` под каждой завершенной задачей — evidence живёт там, а не в маркерах в исходном коде.

## Lazy Decomposition (Ленивая декомпозиция)

Стратегия минимизации раздувания контекста: задачи на старте создаются на высоком уровне, а агент реализации выполняет **In-place Декомпозицию** только для текущей активной задачи.

## In-place Декомпозиция

Процесс уточнения сложной задачи путем добавления вложенных подзадач (например, `T1.1.1`) прямо в `tasks.md` на фазе реализации.

## Smart Branching (Умное ветвление)

Функция, обеспечивающая согласованность разработки в Git путем проверки соответствия текущей ветки ожидаемому шаблону `feature/<slug>`.
